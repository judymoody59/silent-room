# 2. Rooms are created on first connection and destroyed on last departure

Date: 2026-09-24

## Status

Accepted

## Context

이 서비스는 사용자 인증·계정 관리를 두지 않는다 (`.ai/project/scope.md`,
`.ai/AI_AGENT.md` 1장). 방이 언제 생기고 언제 사라지는지에 대한 근거가 명세 이전 단계에서는
비어 있어, 방 생성 경로를 어떤 형태로 둘지 결정이 필요하다.

### 검토한 대안

| 선택지 | 기각 근거 | 되돌리기 비용 |
|---|---|---|
| (가) 첫 WebSocket 연결이 해당 `roomId` 의 방을 만들고, 마지막 참가자의 연결 종료로 폐기 | 채택 | — |
| (나) 별도 방 생성 API 를 두고 그 뒤에 참가 연결을 받는다 | 이 이슈의 범위를 확장한다 — `application` 유스케이스와 `adapter.in.http` 신설이 추가로 필요해지고, 사용자 인증 없는 서비스에서 생성 권한 근거가 새로 필요해진다 | 큼 — 유스케이스 신설·저장 구조 변경·클라이언트 계약 변경으로 번진다 |
| (다) 이 이슈에서 결정을 미룬다 | 결정 지연일 뿐이고, WebSocket 어댑터를 만들 이 이슈에서 반드시 다시 결정해야 한다 | — |

## Decision

우리는 방을 **첫 WebSocket 연결로 성립시키고, 마지막 참가자가 나가는 순간 폐기**한다.
사전 방 생성 API 는 두지 않는다. 별도 생성 API(나)는 이 이슈의 범위를 넘고, 미루기(다)는
같은 결정을 곧 다시 해야 하는 지연이라 택하지 않는다.

- 존재하지 않는 `roomId` 로의 첫 연결이 그 방을 만든다.
- 참가자 수가 0 이 되는 순간 그 방을 폐기한다. 남은 재실 명단·이름 배정은 남기지 않는다.
- 같은 `roomId` 로의 다음 연결은 이전 방과 무관한 새 방을 얻는다.

## Consequences

- `adapter.in.ws` 만으로 방 수명주기가 성립한다. 이 이슈에서 HTTP 어댑터를 만들지 않는다.
- 방 상태는 인스턴스 로컬 메모리에 있다 (`.ai/project/architecture.md`, `.ai/AI_AGENT.md` 4장).
  인스턴스 간 공유가 필요해지는 요구가 오면 별도 결정 대상이다.
- `roomId` 는 서버가 발급하지 않는다 — 클라이언트가 정한 값이 곧 방 식별자가 되므로,
  서로 아는 사람들이 같은 `roomId` 로 접속하는 방식으로 방 공유가 이뤄진다. 이 계약을
  뒤집으려면 방 생성 API 도입과 함께 다시 결정해야 한다.
- 사전 생성 API 가 없으므로 관리자 개념·소유자 개념이 이 리포에 생기지 않는다.
